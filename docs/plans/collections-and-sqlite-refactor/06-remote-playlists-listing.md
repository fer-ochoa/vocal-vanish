# Feat 06 — List the logged-in user's own kara.moe playlists as collections

## Goal

When logged in (feat 03), fetch the **logged-in user's own kara.moe playlists** (`GET /playlist?filter=&order=&byUsername=<me>&includeUserAsContributor=true` — filtered server-side, see the Reference section) and expose each one as a `remote-own` collection the user can browse (metadata + ordered song list) using the same detail view built in feat 05. **No download behavior yet** — that's feat 07. This feat is "see your own kara.moe playlists inside vocal-vanish," read-only against the local library (songs are flagged downloaded/not, nothing is fetched to disk).

This is deliberately **playlists**, not the kara.moe favorites list. Favorites (`GET /favorites`) is a single flat, order-less `{kid}` set that kara.moe does not model as a playlist; playlists are named, ordered, and plural — which is what "collection" means everywhere else in this plan (and what the `collections` table's `name`/`position` columns exist for). So one local `remote-own` row **per remote playlist**, not one row for the whole account. Favorites are out of scope here (see "Explicitly not in this feat").

Functional state after this feat: everything from feats 01–05 still works unchanged when logged out (no `remote-own` collection exists without a session). When logged in, the Collections screen additionally shows the user's kara.moe playlists as `remote-own` entries alongside local collections; opening one shows its songs in the remote's order, each row flagged as already-downloaded or not against the local `songs` table.

## Reference

- Design doc §4 (`getPlaylists`/`getPLC` endpoints, playlist ↔ collection mapping), §1 (dedup must be against the **global** `songs` table, never per-collection — a playlist song the user already downloaded standalone must show as downloaded here too), §3.3 (`collections.id` "kara.moe's own collection/playlist id, OR a locally-generated uuid"), §5 (`kara:collection-browse` channel, described as returning rows flagged downloaded against the global table).
- **The playlist-list endpoint** — `GET /playlist` is **public, no auth** and returns a flat array of playlist objects: `{plaid, name, description, slug, karacount, duration, created_at, modified_at, flag_visible, flag_visible_online, username, nickname, avatar_file, favorited, contributors[]}`. The published swagger for this route is out of date; the four params to build on are below (verified live on 2026-11-04 against `https://kara.moe/api`, the Karaoke Mugen Server REST surface):
  - `filter=<text>` — free-text match over playlist name **and** description (e.g. `filter=nostalgie` matched "A écouter" and "Nostalgie animé").
  - `order=<az|recent|karacount|duration|username>` — user-facing semantics: `az` = alphabetically by name, `recent` = more recent first, `karacount` = number of songs in the playlist, `duration` = playlist duration, `username` = owner username alphabetically. (Heads-up from a live probe: `?order=recent` came back ordered by `created_at` ascending and `karacount`/`duration` ascending, i.e. the opposite of "more/most first" — verify the direction once while implementing and reverse client-side if needed so the label and the list agree.) An invalid value is a hard `400` with `INVALID_DATA` listing the allowed options, so validate against the enum client-side rather than passing user input through.
  - `byUsername=<username>` — return **only that user's** playlists. Case-insensitive (`MEIKO` works); an unknown user yields an empty array, not an error.
  - `includeUserAsContributor=true` — combine with `byUsername` to also return playlists that user merely **contributes to** (verified: a user with 5 own playlists returned 6 with this flag). Presence-only: any non-empty value (`true`, `false`, `0`, `no`) behaves the same, and omitting it excludes contributed playlists — so the *only* way to get "not contributed" is to leave the param off entirely. Do not pass `includeUserAsContributor=false` expecting to exclude them.
  - **Usage pattern, per the upstream app:** fetching playlists across **all users** passes only `filter` and `order`; fetching the **logged-in user's** playlists passes all of `filter`, `order`, `byUsername=<me>`, `includeUserAsContributor=true`.
  - The route returns the whole filtered array in one response, so page client-side if a broad filter returns a lot. Always pass `byUsername` or `filter`: unfiltered, the array is ~1477 rows / ~600 KB.
- `GET /playlist/{plaid}?from=&size=&filter=` — **public, no auth**. Returns `{infos: {count, from, to}, i18n: {...}, avatars: {...}, content: [playlistContent...]}`. Each content row is a full song object (`kid`, `titles`, `songname`, `duration`, `mediafile`, `hardsubbed_mediafile`, `mediasize`, `series`/`singers`/`songtypes`/… tag arrays) **plus** playlist fields `pos` (1-based order), `plcid`, `plaid`, `flag_favorites`, `nickname`, `username`, `added_at`. `from`/`size`/`filter` **do** work here (`from=2&size=3` → `count: 137, from: 2, to: 5`, 3 rows, `pos` 3..5), so this is the route that needs a paging loop.
- Both routes are public. Auth is a **Bearer JWT** (confirmed by feat 03), and any invalid `Authorization` header turns even these public routes into `403`, so the playlist calls in this feat must not send the header at all. (The token is not needed to read playlists — only the `account` table's `username` is needed, and that's local.)
- `GET /favorites` (what the old version of this feat used) is auth-only, returns `[{kid}]` with no order and no batching metadata; it is **not** used by this feat.

## Scope

### Add
- **A small kara.moe API client addition** (alongside the existing `httpGetJson` in `src/index.ts`, or in a new `src/kara-api.ts` — **recommended**, this file is large by now; if factored out, keep `httpGetJson`/`songToRow` there and re-export so feat 03's login code keeps working):
  - `getMyPlaylists(username, { filter?, order? })`: `GET /api/playlist?filter=<filter>&order=<order>&byUsername=<username>&includeUserAsContributor=true` — **without** an `Authorization` header (public route; a stale token turns it into a `403`). Pass `filter` and `order` exactly as the upstream app does for "my playlists" (all four params), and default `order` to `az` (for a "most recent first" control use `order=recent` and verify the direction once — a live probe returned it ordered by `created_at` ascending, so reverse client-side if the server disagrees with the label). `includeUserAsContributor=true` is a deliberate choice: it makes the list match what the user sees in kara.moe's own app, and `collections.ownerUsername` can hold the actual `playlist.username` for contributed ones (which differs from the account's own username — display "by <username>" so a shared playlist isn't mistaken for your own). If you'd rather list strictly your own, drop the param — but note that passing `includeUserAsContributor=false` does **not** exclude contributed playlists, you must omit it.
  - `getPlaylistContents(plaid)`: `GET /api/playlist/{plaid}` paginated (`from`/`size`, page size 100 is comfortably within limits), looping until `infos.to >= infos.count`. Public too — no `Authorization` header needed.
  - Both should reuse the existing error convention (`HTTP <status> for <url>`). Neither call sends an `Authorization` header, so a `401`/`403` there means "we (wrongly) attached a token" or an upstream change — surface the status plainly rather than pretending it's a session-expiry issue. A `400 INVALID_DATA` from a bad `order` value means the enum drifted upstream; treat it as a programmer error, not a user-facing failure.
- **`src/db/queries.ts`**:
  - `upsertRemoteOwnPlaylist(plaid, name, ownerUsername): CollectionRow` — id is the remote `plaid` (design doc §3.3 already allows this: "kara.moe's own collection/playlist id"), `source: 'remote-own'`, `ownerUsername` set, `createdAt` on insert / `updatedAt` + `lastSyncedAt` bumped on update. Upsert, not insert, keyed on `id = plaid`, so repeated syncs never duplicate rows and a renamed remote playlist just updates `name`.
  - `replaceCollectionMembership(collectionId, orderedKids)` — the ordered delete-and-reinsert transaction from design doc §3.6 (same helper feat 05's `reorderCollection` uses; extract it and have both call it, rather than duplicating the transaction). Note the design-doc version bumps `lastSyncedAt` unconditionally, which is correct here (a sync *is* a sync) but must stay conditional for `local` collections per feat 05.
  - `pruneRemoteOwnPlaylists(ownerUsername, keepPlaids: string[])` — delete `remote-own` rows owned by that account username whose `plaid` is no longer returned by kara.moe (playlist deleted, made private, or the user lost contributor access). **Cascade only removes `collection_songs` rows** — never `songs` or files. Two wrinkles to handle explicitly: (a) with `includeUserAsContributor=true` a returned playlist's `username` is the *owner*, not necessarily the logged-in user — key the prune on `plaid` membership in the fetched set, not on `ownerUsername`, or contributed playlists will be re-created and deleted on every sync; (b) "playlist no longer on kara.moe" is a normal, non-alarming event, so the safest variant is to leave the row and mark it stale instead of deleting it. Pick one and document it in the commit message.
  - Note: because `collection_songs.kid` FK-references `songs.kid`, a `remote-own` collection can only hold **local** songs. Feat 06 therefore stores membership only for songs the user already has; the rest are kept in the fetched list and shown as "not downloaded" without a `collection_songs` row. (Feat 07 fixes this properly — read its "Prerequisite" note.)
- **`src/index.ts`**: new `kara:collection-sync-remote-own` handle channel (an explicit "Sync now" action rather than folding it into `kara:collections-list`: the list read must stay instant and offline-capable, and the design doc's `lastSyncedAt` only makes sense for an explicit, network-using action). Signature `{filter?: string, order?: 'az'|'recent'|'karacount'|'duration'|'username'}` so the UI's sort/filter map straight onto the API. Behavior: read `username` from the `account` table (renderer never sees the token), `getMyPlaylists(username, {filter, order})`, upsert one `remote-own` row per playlist (counts from `karacount` until the playlist has been opened once), and re-fetch contents (+ snapshot, + membership) for the playlists the user has opened before so a re-sync reflects the current remote order. Returns the refreshed `CollectionRowWithCount[]` so the renderer can re-render from one call. If not logged in → return the current list unchanged (no throw), so the Collections screen can call it unconditionally.
- **`src/preload.ts` + `src/global.d.ts`**: mirrored `collectionSyncRemoteOwn()` method, typed with the existing `CollectionRow`/`CollectionRowWithCount` interfaces.
- **`src/views/CollectionsView.vue`**: when logged in (via `accountStatus()`), show the `remote-own` collections with their source badge (already handled by `sourceBadgeClass`), their song count, and a "synced Xm ago" line from `lastSyncedAt`, plus one global "Sync now" button for all of the user's playlists. Optionally a small sort control mapping directly onto the API's `order` enum (`az` / `recent` / `karacount` / `duration` / `username`) plus a `filter` text box — both are cheap now that the endpoint sorts and filters server-side, and re-syncing with a different `order` is the whole implementation. Route rows to `CollectionDetailView.vue` like any other collection. Note `listCollectionsWithCounts()` counts `collection_songs` rows, i.e. **downloaded** songs only — for `remote-own` rows show "X of Y downloaded" (Y from `karacount`, stored at sync time) rather than a bare count, or the numbers will look wrong and confusing.
- **`src/views/CollectionDetailView.vue`**: for a `remote-own` collection, load rows from the persisted remote snapshot (see "Where the remote count and snapshot live" below) instead of `collectionSongs()` alone, and for each row: downloaded → normal Play button; not downloaded → "not downloaded" badge, no Play button (nothing on disk yet — download comes in feat 07). Also hide "Remove from collection" on `remote-own` rows (see below).
- Reordering a `remote-own` collection is **not** offered in this feat (order comes from kara.moe; writing order back would be a two-way sync, deferred).

### Where the remote count and snapshot live

`collection_songs` can only reference local songs (FK above), so a remote collection's true size isn't derivable from it. Two small schema additions in this feat:

- `collections.remote_item_count INTEGER` (nullable) — set from `karacount` on every sync, so the Collections list can render "X of Y downloaded" without an extra per-row query.
- The ordered remote snapshot itself (full ordered list of `{kid, pos, title/series/singer/duration as fetched}`) — needed so `CollectionDetailView` can show not-yet-downloaded rows. Either a `remote_items_json` text column on `collections` or a small `remote_playlist_items(plaid, kid, position, payload)` table; feat 07's "download all missing" reads whichever you pick, so choose the one that makes that loop simplest (a table wins if playlists are large, because individual rows can be updated as songs download).

No migration tooling: the app runs idempotent DDL at startup, so both additions must be issued defensively (`PRAGMA table_info(...)` → `ALTER TABLE ... ADD COLUMN` only if missing), consistent with the plan's "no migrations" stance.

### Explicitly not in this feat
- **No favorites-as-a-collection.** `GET /favorites` stays untouched: it is auth-only, order-less, and not a playlist. It may still be worth showing a "Favorites" pseudo-collection later, but that is a separate decision (and would be one synthetic row, not a `remote-own` playlist) — do not half-wire it here.
- No download action from this view (feat 07) — not-downloaded rows just show their flag.
- No `remote-subscribed` (other users') collections (feat 08).
- No two-way sync: renaming, reordering, adding or removing a song in-app does not call `PUT /playlist/{plaid}`, `POST /playlist/{plaid}`, `DELETE /playlist/{plaid}` or `/playlist/content/edit`. Feat 05's "Remove from collection" action must therefore be **disabled/hidden for `remote-own` rows** in this feat (this is the resolution of the flag feat 05 raised) — do it explicitly so the button isn't silently present-but-broken.
- No auto-sync on login or on app start; only the explicit "Sync now" action. (Cheap to add later; keeps this feat's network behavior predictable.)

## Acceptance criteria

- Logged out: Collections screen shows exactly what feats 04/05 showed (no `remote-own` rows, no crash, "Sync now" hidden or disabled), and `kara:collection-sync-remote-own` returns the list unchanged rather than throwing.
- Logged in with ≥2 playlists on kara.moe: "Sync now" issues exactly one `GET /playlist?filter=&order=<chosen>&byUsername=<me>&includeUserAsContributor=true` and creates **one** `remote-own` row per returned playlist, named after the remote playlist; each row's song count matches `karacount`. Spot-check the returned plaid list against kara.moe itself.
- `byUsername=<me>` is actually used (not a client-side filter): the request's payload should be proportionate (~39 KB for 65 playlists, vs ~600 KB for the unfiltered list), and another user's playlists must never appear unless the user is a contributor of them.
- With `includeUserAsContributor=true`, a playlist the user only contributes to appears and is labelled with its real owner (`playlist.username`), not as the user's own; omitting the param (if you scope this feat to strictly-owned playlists instead) removes it.
- Changing the sort control re-syncs with the matching `order` value and the list order matches what the control promises (`az` / `recent` / `karacount` / `duration` / `username`), accounting for the direction the server actually returns (reverse client-side if the server sorts ascending where the label says "most first").
- Typing in the filter box re-syncs with `filter=<text>` and both name and description matches come back (e.g. a word that only appears in a description).
- An out-of-range `order` never reaches the network (client-side enum) and a `400 INVALID_DATA` would be reported as a bug rather than shown as a user error.
- Opening a `remote-own` collection shows every song in the remote order (verify against `GET /playlist/{plaid}` directly for one playlist, including a multi-page one — e.g. `from=2&size=3` semantics), with downloaded/not flags matching the local library: download one playlist song from Search first, then sync — that song shows downloaded, others don't.
- Re-syncing twice in a row does not duplicate `collections` rows (upsert on `plaid`) and does not duplicate membership/snapshot entries.
- A playlist that was deleted or made private on kara.moe between syncs is handled per the chosen prune policy (removed, or kept-and-marked-stale) with no orphaned rows and no deleted local songs; confirm in Catalog that all underlying songs are still present.
- Renaming a playlist on kara.moe and re-syncing updates the local `name` (not a second row).
- "Remove from collection" and reordering are absent/disabled on `remote-own` rows; Play works only for downloaded rows.
- `401`/`403` while the local session is unusable must not silently disable the feature: playlist fetching is public, so a `403` caused by sending a stale token should be fixed by not sending it (and a genuinely expired session must be reported as "log in again" from feat 03's `accountStatus`, not inferred from a playlist call).
- `npm run lint` passes; manual verification against the real kara.moe API with a test account that has at least two playlists, one of them longer than one page.
